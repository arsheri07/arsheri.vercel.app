    Credential Leak Scanner

    Nov 2026 · personal project · 43 tests
    github.com/arsheri07/credential-leak-scanner

    A command-line tool that catches leaked API keys, tokens, and passwords in code and in git history, before they reach a public repo.

    PythonRegexShannon entropy GitSARIFGitHub Actionspytest
    try it · scan a config filecredscan --stdin
    findings=0 verdict=pass

      Committing a credential is one of the most common ways cloud accounts get compromised, and deleting it in the next commit doesn't help: the key is still in the history for anyone who clones the repo. Credential Leak Scanner checks files, directories, and every line ever added in git history, then reports the file, line, and commit where each secret appeared.

      It ships 13 detection rules (AWS, GitHub, Slack, Stripe, Google, Anthropic, and OpenAI keys, PEM private keys, JWTs, passwords inside database URLs, and hard-coded password = "..." assignments). Output comes as readable text, JSON, or SARIF, which GitHub code scanning reads directly. Exit codes make it work as a pre-commit hook or a CI gate.

      Pure Python standard library, no dependencies. 43 pytest tests cover every rule, the false-positive cases, redaction, and a repo where a secret is committed and then deleted. The tests build their fake keys at runtime, so the repo passes its own scan.

      The decision

      Regex alone flags too much: password = "changeme123" matches the same pattern as a real one. So every match also has to clear a Shannon entropy threshold and a placeholder check (example, ${VAR}, os.environ). Real keys are random; placeholders aren't. And findings are always redacted to the first and last four characters, because a scanner whose report leaks the secret just moves the leak somewhere else.

      KitchenSense

      Aug 2026 · hackathon · 48 hours · solo
      github.com/arsheri07/kitchen-sense

      Photograph your fridge and pantry; get back a structured inventory and a week of meals planned around what you actually have.

      Node.jsTypeScriptPostgreSQL Claude APIS3-compatible storageZerops
      try it · plan tonight's dinnerallergies filter · preferences rank
      allergies (hard filter: removes recipes)
      preferences (soft rank: reorders only)

        Built solo in 48 hours for The Zerops Challenge, a WeMakeDevs hackathon. The vision layer uses Claude Haiku 4.5 to pull structured inventory data out of ordinary phone photos — the hard part isn't recognizing food, it's turning a cluttered shelf into rows a database can reason about.

        On top of that sits a recipe-matching and meal-planning engine covering a 38-recipe catalog, with an urgency-aware greedy scheduler that pushes ingredients closest to spoiling into earlier meals.

        The backend runs as a two-service dev/stage pipeline on Zerops, with database migrations that apply atomically and automatically on every deploy. I drove the whole build-deploy-debug loop through Claude Code and Zerops' control-plane tooling, debugging against live logs rather than clicking through a cloud console.

        The decision

        Dietary preferences are split into a hard filter and a soft rank. Restrictions — allergies, things you can't eat — are enforced absolutely and remove recipes from consideration. Preferences only influence ordering. Collapsing both into one score would have been simpler and occasionally dangerous.

        Canary

        Sep 2026 · personal project · 36 tests
        github.com/arsheri07/canary

        A file integrity monitor that tells the difference between you editing a file and ransomware encrypting it.

        PythonSHA-256Shannon entropy LinuxCLI
        try it · entropy checkcanary --scan
        0typical text ≈ 4.4encrypted ≥ 7.9
        entropy=0.00 verdict=pass

        Point it at a folder and it fingerprints every file with SHA-256. Run it again later and it tells you exactly what was added, modified, or deleted. File integrity monitoring is a required control under PCI-DSS 11.5 and CIS Control 3 — Tripwire and OSSEC are the commercial versions of this idea.

        The harder problem is interpretation. Forty files changing could be a build finishing, or it could be ransomware working through your documents. Six signals contribute to a score, because any one of them has an innocent explanation and almost nothing legitimate produces several at once.

        Ransomware doesn't announce itself, but it does have to encrypt. That's the property this leans on: encryption is designed to produce output indistinguishable from noise, and noise looks measurably different from English text.

        The decision

        Detection uses Shannon entropy — a measure of how unpredictable a file's bytes are, from 0 to 8. Ordinary text sits around 4.4 because it's full of repeated letters and spaces. Encrypted data sits above 7.9 because every byte value is equally likely. Testing against thirty documents encrypted in place, with no renamed files and no ransom note, entropy moved from 3.80 to 7.85 on every one. Extension and filename matching detect nothing in that case. Entropy still catches it.

        Phishing Risk Analyzer

        Aug 2026 · personal project · 84 tests
        github.com/arsheri07/phishing-risk-analyzer live demo

        One risk-scoring engine that reviews emails, websites, texts, and app listings through real email authentication, not pattern matching.

        PythonFlaskSPF/DKIM/DMARC pytest
        try it · score an emailclick a verdict to flip it
        from: billing@northbank.com
        subject: Your statement is ready
        spf=
        dkim=
        dmarc=
        lookalike_domain=
        risk=0/100 verdict=low

        Most consumer scam detectors work by pattern-matching sender names and obvious red flags — easy to build, easy for an attacker to route around with a lookalike domain. Phishing Risk Analyzer does the actual protocol verification instead: SPF, DKIM, and DMARC checks, including real DKIM signature validation against the sending domain's published public key in DNS.

        That verification answers one specific question — does this message genuinely come from the domain it claims to? It doesn't answer whether that domain deserves your trust, which is why lookalike-domain detection runs as a separate layer on top.

        Built independently: the Flask REST API, the scoring engine, and the interface, backed by 84 pytest tests covering the protocol logic.

        The decision

        Verifying DKIM properly means fetching the sender's public key from DNS and validating a cryptographic signature — not just checking that a header field exists. Skipping that and trusting the header at face value would have been much simpler, and nobody would have known the difference from the outside. A detector that only catches obvious scams isn't a detector.
